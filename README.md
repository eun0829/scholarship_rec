# 외부 장학금 수집·추출·저장 (외부01 구현)

학교 홈페이지 장학공지 게시판(게시판 374) → 본문/첨부 수집 → 텍스트 추출 → AI 자격요건 구조화(JSON) → Oracle 저장.
추천(학생 프로필 매칭) 단계는 이 결과(`SCHOLARSHIP_NOTICE`)를 읽어서 별도로 붙인다.

## 처리 흐름

1. 쿼리01/02 로 최근 N일 공고와 첨부 목록 조회 (연결 키 `BBS_ARTCL_SEQ`)
2. 본문 HTML → 텍스트 (표는 `행 | 셀`), 내용 해시 계산 → 변경 없으면 건너뜀
3. 첨부: 파일명 분류(요강/양식/보조/제외/미분류) → 제외·미지원은 다운로드 안 함 → `https://www.tukorea.ac.kr/bbs/tukorea/374/{첨부번호}/download.do` 로 NAS 저장
   → 형식별 텍스트 추출 (HWP/HWPX/PDF/DOCX/XLSX/ZIP, 이미지·스캔 PDF 는 AI 이미지 입력)
4. AI 입력: 본문 + 요강 첨부 + (양식/보조는 "참고"로 낮은 우선순위) + 텍스트가 부족할 때만 이미지(본문 포스터 포함)
5. AI JSON → 코드 검증(날짜·요일·성적 만점 단위 등) → 이상이 있으면 `NEED_REVIEW`
6. 원본에서 사라진(삭제/비공개) 글은 `USE_YN='N'`, 다시 나타나면 복구

저장 경로: `/info/ai_bundle/scholarship/ext01/{글번호}/{첨부번호}.{확장자}` (원본 파일명은 DB에만 보관)

## 이미 저장된 글 처리 규칙

| 상황 | 기본 동작 |
|---|---|
| 글번호가 이미 있고 **완료**(`EXTRACTED`/`NEED_REVIEW`) 상태 | **건너뜀**. 내용이 같으면 `변경없음`, 바뀌었으면 `건너뜀(내용변경)` 으로 집계하고 로그에 남김 |
| 글번호가 있지만 **미완료**(`COLLECTED`/`FAILED`) | **이어서 처리** (`--no-ai` 로 먼저 모은 글을 AI 로 마저 처리, 실패 재시도) |
| 글번호는 새 것인데 **제목이 같은 활성 글**(`USE_YN=Y`)이 이미 있음 | **건너뜀** (`건너뜀(제목중복)`). 공백/HTML 엔티티 차이는 무시. 원본에서 사라진(`USE_YN=N`) 글과는 비교하지 않음 |
| `--force` | 위 규칙을 모두 무시하고 다시 처리 |

- 옵션: `--update-changed` (완료된 글도 내용이 바뀌면 재처리), `--no-skip-title` (제목이 같아도 처리). `.env`: `UPDATE_CHANGED=true`, `SKIP_SAME_TITLE=false`
- **주의**: 기본 설정에서는 원본 글을 **수정해서 마감일 등이 바뀐 경우**를 반영하지 않습니다 (로그의 `건너뜀(내용변경)` 건수로 확인). 마감일 오류는 영향이 크므로 운영 시 `--update-changed` 사용 여부를 정하세요.
- 제목이 같은 글이 정정/재게시일 수 있어 건너뛴 글은 DB 에 저장되지 않습니다 (로그에 기존 글번호 표시).

## 외부02 (드림스폰) - 수집 / 추출 / 저장

```
python run_ext02.py --list-only                          # 목록만 확인 (로그인/DB/AI 불필요) - 가장 먼저
python set_secret.py --test-dreamspon                    # 목록 -> 로그인 -> 상세 본문 읽기 확인
python run_ext02.py --dry-run --no-ai --limit 3 --dump-dir out   # 로그인 + 상세/첨부 수집 (DB 저장 없음, AI 비용 없음)
python run_ext02.py --no-ai --limit 3 --dump-dir out     # 위와 같고 DB 에 COLLECTED 로 저장
python run_ext02.py --limit 3 --dump-dir out             # AI 포함 3건 (크레딧 소모: 실행 전후 python set_secret.py --credits)
python run_ext02.py                                      # 전체 (이미 저장된 글은 상세를 조회하지 않음 = 로그인도 안 함)
python run_ext02.py --refresh                            # 저장된 글도 상세를 다시 읽어 신청기간 변경을 반영 (AI 호출 없음)
python run_ext02.py --only 9218 --force                  # 특정 글만 다시 처리
```

- **흐름**: 목록(로그인 불필요) -> `config/ext02.json` 의 종류/대상 태그/상태로 후보 선별(기본: `#장학금` + `#대학생`, 모집완료 제외) -> 새 글/미완료 글이 있을 때만 로그인(1회) -> 상세 -> 첨부(POST `/process/fileDown.html`) -> 추출 -> AI -> 저장 (`SRC_CD='EXT02'`, 글번호=드림스폰 idx)
- **`--limit N`** 은 마감 임박순 앞 N건입니다 (이미 저장된 글도 앞 N건에 포함되며 건너뜁니다).
- **로그인**: `POST /process/checkuser.html` (사이트 JS 와 같은 항목). 실패하면 계정 보호를 위해 **자동 재시도 없이 중단**합니다. 비밀번호는 로그/오류에 남기지 않고, 세션 쿠키는 메모리에만 둡니다. 세션이 풀리면 실행당 최대 2회 다시 로그인합니다. 요청 간격은 `delay_sec`(기본 2초).
- **고정 7개 항목**(신청기간/선발인원/장학혜택/접수방법/지원대상/신청자격/장학금 문의)은 코드가 직접 나눠서 `SCHOLARSHIP_NOTICE.SRC_FIELDS_JSON` 에 저장합니다 (AI 해석인 `ELIG_JSON` 과 분리). 기관정보, 원문공고 URL, 목록 정보(태그, 최초 D-day)도 함께 저장합니다. 없는 항목은 비우고 모르는 제목은 `extra_sections` 에 보존합니다.
- **날짜 컬럼(`APPLY_START`/`APPLY_END`)**: 코드가 신청기간을 확정하면 **수집 단계(AI 전, `--no-ai` 포함)에서 바로** 저장합니다. 읽을 수 없으면 비워 두고(D-day 추정은 AI 단계에서 검수 표시와 함께), 이미 있는 값은 빈 값으로 덮어쓰지 않습니다.
- **마감일 우선순위**: 상세 본문 `신청기간` > 정보표의 신청기간 > (없을 때만, 최초 저장 때만) 목록 D-day 추정 > 없음. AI 가 읽은 마감일과 다르면 **신청기간 값을 사용하고 `NEED_REVIEW`** 사유로 남깁니다. 요일이 날짜와 맞지 않으면 경고합니다. D-day 추정이나 마감일 없음도 검수 사유입니다.
- **코드가 채우는 값**: 선발인원(`recruit_count`), 혜택 첫 줄(`amount`, AI 가 비웠을 때), 접수방법(`apply_how`), 접수방법 키워드로 신청 방식(`APPLY_TYPE`, AI 와 다르면 검수), 지원대상의 학교급(`target_levels`, AI 가 비웠을 때).
- **첨부 (`EXT02_ATTACH_TO_AI`, 기본 `guide_only`)**: 모든 첨부를 받아서 파일별 텍스트를 저장하지만, AI 에는 **공고문(요강)과 이름으로 분류가 안 되는(미분류) 첨부만** 보냅니다. 지원서/양식류(`지원서, 신청서, 서식, 양식, 동의서, 추천서 ...`)는 저장만 하며, 이런 파일의 처리 실패는 검수 사유가 아닙니다. `guide_and_form`(양식은 앞 4,000자), `none`(본문만)으로 바꿀 수 있습니다.
- **공고문 첨부 여부**는 AI 가 아니라 코드가 `SRC_FIELDS_JSON.attachment_check` (`guide_attached`, 역할별 추출 건수)에 기록합니다. "요약 본문만 있다", "제출서류가 공고문 안내 확인뿐" 같은 사실은 AI 가 `uncertain(verify)` 로 적지 않도록 안내해서, 이런 글이 모두 `NEED_REVIEW` 가 되는 것을 막습니다 (자격 판정에 쓰이는 값이 실제로 모호하거나 충돌할 때만 검수).
- **ZIP** : 압축 안의 파일을 **각각** 요강/양식/참고/제외로 분류합니다 (이름만으로 분류가 안 되면 ZIP 이름이 양식류일 때 그 분류를 따름). 파일마다 `SCHOLARSHIP_NOTICE_FILE` 한 행(`FILE_SEQ` = `번호-해시.순번`)이 생기고, ZIP 자체의 행은 `DOWNLOADED`(`EXTRACT_METHOD='ZIP'`)입니다. 암호 걸린 파일, 변환 실패, 중첩 ZIP, 지원하지 않는 형식(`.doc`, `.egg`, `.alz`, `.7z`, `.rar` 등)은 그 파일만 실패/건너뜀입니다. (외부01 의 ZIP 도 같은 방식으로 처리됩니다.)
- **변경 감지**: 7개 항목과 첨부 이름으로만 해시를 만들어 조회수/D-day/광고 변화는 무시합니다. **신청기간만 바뀌면 AI 호출 없이** 날짜 컬럼, `SRC_FIELDS_JSON`, `ELIG_JSON` 의 날짜만 갱신합니다 (`--refresh` 필요). 다른 내용이 바뀌면 기본은 건너뜀(`--update-changed` 로 재처리).
- **사라진 글**: 전체 실행에서 목록에 없는 EXT02 활성 글을 비활성화합니다 (게시일 범위가 아니라 활성 글 전체 기준). **목록 조회가 실패했거나 0건이면 정리하지 않습니다.**
- **DB**: `schema_ext02.sql` (`ALTER TABLE SCHOLARSHIP_NOTICE ADD (SRC_FIELDS_JSON CLOB)`)를 먼저 적용하세요. 컬럼이 없으면 경고만 하고 해당 값 저장을 건너뜁니다. 확인 쿼리는 `check_ext02.sql`.
- **개인정보**: 상세 HTML 의 문의/오류 제보 양식(로그인 계정 이메일 포함), 광고, 면책 문구는 읽지도 저장하지도 않습니다. 서버 내부 파일 경로(`data-filepath`)는 다운로드 요청에만 쓰고 저장하지 않습니다.
- **알려진 한계**: 7개 항목이 모든 글에서 같은 형식인지는 샘플 1건으로만 확인했습니다 (다른 형식은 없는 항목/`extra_sections` 로 처리). 로그인 후 상세 열람, 첨부 다운로드(`file1`=목록의 경로 값)는 실제 사이트에서 첫 실행 때 확인이 필요합니다. 원문 공고 사이트(외부 재단)는 따라가지 않고 링크로만 안내합니다.

## 외부02 학생 정보 조건 조사 (1회성, AI·DB 없음)

외부 장학 판정에 필요한 학생 정보를 **실제 모집공고 본문**에서 도출하기 위한 조사 도구입니다. 목록의 해시태그로 결론을 내지 않고 상세의 고정 7개 항목을 읽습니다. 마감된 공고도 포함하며, 기존 수집(`run_ext02.py`)과 독립이라 DB에 아무것도 저장하지 않고 AI(크레딧)도 쓰지 않습니다. 드림스폰 계정은 `set_secret.py`에 저장한 값을 씁니다.

```
python run_ext02_survey.py --list-only           # 조사 대상 목록만 확인 (로그인 불필요)
python run_ext02_survey.py                       # 최근 100건 상세 수집 (로그인, 약 5~8분)
python run_ext02_survey.py --attachments         # 공고문(요강) 첨부 텍스트까지 (양식은 받지 않음)
python run_ext02_survey.py --resume              # 중단된 수집 이어서
python run_ext02_survey.py --count 150 --kinds "" --audience ""    # 종류·대상 조건 없이 전부
```

- **대상**: 기본은 `장학금` + `대학생` 대상 공고를 **등록이 최근인 순(idx 큰 순)** 으로 100건. 목록은 정렬 방식(`--ordby`, 기본 5=업로드순, 4=모집완료, 0=기본)을 차례로 훑다가 대상이 충분히 모이면 멈춥니다. 목록에서 찾을 수 있는 대상이 100건보다 적으면 있는 만큼 조사합니다.
- **결과** (`survey_ext02` 폴더): `ext02_survey_notices.txt`(공고별 전체 본문, 분석용), `ext02_survey_summary.txt`(코드가 센 1차 통계: 지원대상, 접수방법, 신청자격 이름표, 학생 정보 개념별 언급 공고 수와 예시 문구), `ext02_survey_notices.jsonl`(구조화), `--attachments` 사용 시 `ext02_survey_guides.txt`.
- 통계의 개념 키워드는 1차 훑어보기용입니다. 같은 단어가 조건이 아닌 설명에 나올 수 있어 최종 결론은 본문을 직접 읽고 정리합니다.
- 개별 공고의 상세를 읽지 못해도 조사는 계속되고 요약에 실패 목록이 남습니다. 로그인 실패는 자동 재시도 없이 중단합니다.

## 항목 사전과 스키마 v3 (1단계, 기본값은 꺼짐)

학생 항목과 공고 조건 항목을 `config/item_registry.json` **한 곳**에서 정의합니다. 항목을 추가하면 학생 입력 라벨(동의어 포함), 후속 질문 문구, 공고 구조화(AI) 프롬프트의 "항목 사전" 부분이 같은 정의에서 나옵니다.

```
python check_registry.py                 # 사전 점검: 오류 검사 + 요약 (DB·AI 사용 안 함)
python check_registry.py --show-prompt   # v3 프롬프트에 들어갈 '항목 사전' 부분과 전체 길이
```

**켜는 방법**: `.env` 에 `AI_SCHEMA_VERSION=3`. 기본값은 `2`(기존 방식 그대로)이고, v3 는 시험 추출로 AI 가 새 항목을 맞게 채우는지 확인한 뒤에 켭니다. 켜면 ELIG_JSON 에 `schema_version: 3`, `registry_version`, `processed_items`(어떤 사전으로 분석했는지)가 함께 저장됩니다. v2 로 저장된 공고와 판정 코드는 그대로 동작합니다.

**v3 에서 달라지는 것**
- 공고 조건이 더 구조화됩니다: `region.requirements`(본인·부모 주민등록, 졸업 고교, 학교 소재지, 거주 기간), `gpa.basis=LAST_N`(직전 N개 학기 평균), `completed_terms`·`remaining_terms`, `special_groups`(신분 코드와 필수·우대), `waivers`(조건 면제), `gender`, `age`, `major_groups`, `school`, `prerequisites`, `recommendation`, `exclusion_items`, `obligations`, `review_criteria`, 유형(variants)별 마감·신청 방식.
- 사전에 없는 조건은 버리지 않고 `unmodeled_conditions` 에 **원문 그대로**(어느 항목·어느 문서에서 나왔는지, 자격/제외/혜택 제한/절차/의무/심사 구분) 모읍니다. 새 항목을 사전에 추가했을 때 이것만 다시 보면 전체 공고를 다시 분석하지 않아도 됩니다(증분 보강, 다음 단계).
- 유형(variants)마다 마감이 다르면 최상위 `apply_end` 는 가장 늦은 유형 마감으로(`apply_start` 는 가장 이른 시작으로) 채웁니다. 유형별 날짜는 그대로 유지되고, 최상위 마감이 비어 추천 조회에서 빠지는 일을 막습니다.
- AI 가 `※ 중복수혜 : 가능/일부 가능/정보없음` 같은 드림스폰 요약 표기를 조건처럼 적으면 걸러냅니다 (`불가`나 금액·학기 같은 구체적 제한은 남깁니다). 유형은 `nationality` 도 가질 수 있습니다(예: 외국인 유학생).
- 만점이 적혀 있지 않은 성적 기준은 검수 사유가 아니라 `gpa.scale_stated=false` 로 표시합니다(판정에서 4.5 로 가정).
- AI 가 표준 값 목록에 없는 값을 쓰면 값을 버리지 않고 `unmodeled_conditions` 로 옮깁니다. 지역 요건이 둘 이상인데 ANY/ALL 구분이 없으면 검수 사유로 남깁니다.

**항목 하나 추가하는 방법**
1. `config/item_registry.json` 의 `items` 에 항목을 적습니다 (필수: code, label, kind, source, type, tier. 학생이 직접 고르는 항목은 question 도).
2. 공고의 새 조건 필드가 필요하면 먼저 `schema_v3.py` 의 `TEMPLATE_V3` 에 필드를 추가합니다 (사전의 `notice_path` 는 스키마에 있는 경로만 쓸 수 있습니다).
3. 비교 방식이 `gte`/`lte`/`in`/`place_in`/`truthy` 이거나 `custom` 이 기존 함수 이름(점검 명령에 목록이 나옴)이면 코드 변경이 없습니다. 새로운 비교 방식이면 비교 함수를 새로 만들어야 합니다.
4. `python check_registry.py` 로 점검합니다. 오류는 한꺼번에 항목 번호와 이유로 알려 줍니다 (모르는 키, 중복 라벨, 없는 공고 필드 경로, 잘못된 값 범위 등).

설정: `AI_SCHEMA_VERSION`(2 또는 3), `ITEM_REGISTRY_FILE`(기본 `config/item_registry.json`). v3 로 AI 를 쓸 때는 실행 시작 단계에서 사전을 검증하므로, 사전이 잘못되면 AI 를 한 번도 부르기 전에 멈춥니다.

## 스키마 v3 시험 추출 (2단계, AI 크레딧이 듭니다)

조사한 공고 61건 중 20건(`DEFAULT_SAMPLE`)의 **본문만**(첨부 없음) v3 프롬프트로 실제 AI 에 보내고, 제가 읽고 분류한 기대 결과(`data/ext02_survey_expected.json`)와 항목별로 대조합니다. DB 에는 저장하지 않습니다. 목적은 (1) AI 가 사전 항목을 맞게 채우는지, (2) 못 채운 조건이 `unmodeled_conditions`/메모에 원문으로 남는지 아니면 사라지는지, (3) 응답이 잘리거나 검수 사유가 얼마나 생기는지 확인하는 것입니다.

```
python run_v3_trial.py --dry-run     # AI 호출 없이 입력 크기와 예상 크레딧 확인 (먼저 실행)
python run_v3_trial.py --first 5     # 1차: 길고 까다로운 5건 (응답 길이·형식·실제 크레딧 확인)
python run_v3_trial.py               # 2차: 나머지 (이미 성공한 공고는 자동으로 건너뜀)
python run_v3_trial.py --only 9195   # 지정한 공고만 / --force 로 이미 한 공고를 다시
python run_v3_trial.py --report-only # AI 호출 없이 저장된 결과로 보고서만 다시 만들기
python run_v3_trial.py --renormalize # AI 호출 없이 저장된 AI 원문(*_ai_raw.txt)을 현재 코드로 다시 정리하고 보고서 다시 만들기
```

- 공고 본문 파일은 `python run_ext02_survey.py` 가 만든 `survey_ext02\ext02_survey_notices.txt` 입니다 (`--notices` 로 변경).
- 결과 폴더 `v3_trial\`: 공고별 `*_v3.json`(정규화 결과·이슈·토큰), `*_ai_raw.txt`(AI 원문), `v3_trial_report.txt`(보고서), `v3_trial_results.json`(항목별 대조), `credits_log.json`(실행 전후 크레딧 변화, 게이트웨이를 쓸 때).
- **크레딧 안전장치**: 이미 성공한 공고는 다시 호출하지 않습니다(`--force` 로만 재실행). 실패한 공고만 재시도합니다. `--dry-run` 은 AI 를 부르지 않습니다. 키가 없으면 호출 전에 중단합니다.
- 입력의 대부분(건당 약 94%)은 매번 같은 시스템 프롬프트입니다(v3 12,894자, v2 5,523자의 2.3배). 이 클라이언트는 프롬프트 캐시(`cache_control`)를 요청하므로 게이트웨이가 지원하면 실제 소모는 `--dry-run` 추정보다 낮을 수 있습니다.
- 정규화·측정 코드를 고친 뒤에는 `--renormalize` 로 **크레딧 없이** 이미 받은 AI 응답에 다시 적용해 볼 수 있습니다 (프롬프트를 바꾼 경우에는 AI 를 다시 호출해야 하며, 결과에 프롬프트 버전이 기록되어 섞여 있는지 보고서에서 확인됩니다).
- `v3_trial_results.json` 에는 원인 분석용으로 AI 가 쓴 핵심 항목(`ai`: 유형 이름·면제·신분·제외 조건·선행 조건·검수 표시 등)이 함께 저장됩니다.
- 기대 데이터(`data/ext02_survey_expected.json`)는 제가 원문을 읽고 분류한 것이라 틀릴 수 있습니다. 시험 결과와 대조하며 정정한 내역은 같은 파일의 `corrections` 에 **근거 문장과 함께** 기록합니다 (부모만 거주 조건인데 본인 거주로 분류한 3건, '…도 신청 가능' 같은 허용 문구를 조건으로 센 것 등).
- 보고서의 "사라짐"은 구조 항목에도, 사전의 키워드 힌트(`detect_hints`)로 찾은 원문 보존 위치에도 없는 조건입니다. 힌트가 놓친 경우일 수 있으니 [2] 항목의 공고별 목록을 원문과 직접 대조해 확인합니다.

## 학생 정보 텍스트 입력 (3단계, AI·DB 없음)

학생 정보를 `라벨: 값` 텍스트로 받아 프로필로 만듭니다. 라벨 이름·동의어·허용 값·범위는 **항목 사전**에서 가져옵니다.

```
python make_student_text.py --template --out 양식.txt      # 빈 입력 양식 (값 종류별 입력 예시 포함)
python make_student_text.py --check sample_student.txt      # 텍스트를 읽어 보고서만 출력 (경고, 입력에 없는 항목)
python make_student_text.py --from-json student.json        # 기존 프로필 JSON 을 규격 텍스트로
python run_recommend.py --profile-text sample_student.txt --results-dir out   # 텍스트로 추천 (--profile JSON 과 같은 결과)
```

**읽는 규칙**
- 줄마다 `- 라벨: 값`. **순서는 무관**하고 `#` 줄은 무시, `-` 는 있어도 없어도 되며 전각 콜론·띄어쓰기 변형(`직전 학기 평점`)·동의어(`소득분위`)도 읽습니다.
- 괄호 속 설명(`(졸업학기 충족)`, `(성적상승)`)은 **무시**하고 기본 값만 읽습니다 (위쪽 시스템이 계산한 값이 틀릴 수 있어서).
- **한 줄이 틀려도 그 항목만** "알 수 없음"이 되고 나머지는 그대로 읽습니다. 값을 짐작해서 채우지 않습니다 (오타 라벨은 경고, 모호한 라벨(`평점`, `성적`)도 채우지 않음).
- 같은 항목이 **다른 값으로 두 번** 나오면 비우고 경고합니다. 만점이 서로 다른 평점은 줄 순서가 아니라 항목 우선순위(직전학기 평점 > 누적 평점)로 정합니다.
- 값 해석: 평점 `3.79 / 4.5`(만점이 없으면 4.5 가정), 학기 `2026-1`, 지역 `경기도 수원시`, 거주 기간 구간은 **하한값**(`1~3년`→1년), 학기별 성적 `2026-1 3.79 15 | 2025-2 3.11 18`.
- `해당 항목`: **해당 없음**(모두 해당하지 않음으로 확정) / **답하지 않음**(모름으로 둠) / 해당하는 것을 쉼표로 나열(나열하지 않은 신분은 해당 없음). 신분을 항목별로(`다자녀 가정: 해당`) 적어도 되고, 일부만 답하면 나머지를 "해당 없음"으로 단정하지 않습니다.
- **개인정보**: 라벨을 먼저 항목 사전과 대조하고, 사전에 없는 라벨만 개인정보 필터를 적용합니다 (`본인 주민등록` 통과, `주민등록번호`·이름·학번·연락처·상세 주소·이메일·생년월일 차단). 주민등록번호·전화번호·이메일 형식의 **값**도 어느 라벨에서든 받지 않습니다.
- **학교 고정 항목**(학교 소재지·종류·참여 사업)은 서버 설정에서 가져오므로 학생 텍스트에 있어도 무시합니다. 입력 크기 상한은 20KB 입니다.
- 새 항목을 항목 사전에 추가하면 파서가 바로 읽습니다 (전용 프로필 필드가 없는 항목은 `profile.extra` 에 담기고, 값 종류·허용 값·범위 검증은 사전이 정한 대로).

**보고서**: 못 읽은 줄, 모르는 라벨, 값 오류, 충돌, 받지 않은 개인정보 라벨, 그리고 **사전에 있는데 입력에 없는 항목**(필수·권장 이름, 선택은 개수)을 알려 줍니다. `--json` 출력에는 `profile_parse` 로 들어가며, 이 목록은 부족한 입력을 학생에게 다시 묻는 데 쓰입니다(5단계).

**범위**: 새 프로필 필드(부모 주민등록, 졸업 고교, 나이, 성별, 입학년도·구분, 학기별 성적, 학위, 국가장학금 신청, 신분 코드 등)는 프로필에 **담기기만 하고 아직 판정에는 쓰이지 않습니다** (판정 엔진 v3 는 4단계). 그래서 이 단계에서 추천 결과가 달라지지는 않습니다.

## 판정 엔진 v3 - 4-A: 지역·성적·학기 (AI·DB 없음)

`schema_version >= 3` 공고만 새 판정 경로(`matcher_v3.py`)로 갑니다. **v2 이하 공고의 판정은 바뀌지 않습니다.** 판정 원칙은 같습니다: PASS(충족) / FAIL(미달) / UNKNOWN(학생 정보가 없거나 공고가 불명확), 정보가 없다고 탈락시키지 않습니다.

**4-A 가 판정하는 것**
- **지역 요건**(`region.requirements`): 본인·부모 주민등록, 졸업 고교 소재지, 학교 소재지, 거주 기간. `ANY`(하나만) / `ALL`(모두) / `UNKNOWN`(공고가 불명확: 두 해석에서 같은 결과일 때만 단정). 여러 지역은 '또는'.
  - 지명은 `places.py` 가 시·도 / 시·군·구 / 일반구로 나눠 비교합니다. v2 엔진은 `서울특별시 서초구` 같은 한 문자열을 **같은 지역 학생에게도 미달로 판정**했습니다.
  - 공고가 구 단위(`수원시 영통구`)를 요구하는데 학생이 시까지만 적었으면 **확인 필요**, 같은 이름이 여러 시·도에 있는 곳(중구, 동구, 광주 등)은 시·도 없이는 확정하지 않습니다.
  - 거주 기간: 학생 입력이 구간이면 하한으로 '확실히 충족'(PASS), 상한으로 '확실히 미달'(FAIL)을 가르고 그 사이는 확인 필요입니다. 부모의 거주 기간은 입력 항목이 없어 확인 필요로 남깁니다.
- **성적**: 직전학기 / 누적 / 둘 중 하나 / **직전 N개 학기 평균** / 100점제. 직전 N개 학기는 학점 가중 평균과 단순 평균이 **같은 판정일 때만** 단정합니다. `EITHER` 는 한쪽만 알면 미달로 단정하지 않습니다. 입학성적(수능·내신) 기준은 확인 필요입니다. **공고에 만점이 없으면 4.5 로 가정**하고 결과에 알립니다(검수 사유로 삼지 않음).
- **학기 조건**: 이수 학기, 졸업까지 남은 학기. 남은 학기·졸업학기는 학적 값이 없으면 **이수학기와 정규 학기 수(`RECOMMEND_REGULAR_TERMS`, 기본 8)로 계산**합니다(4년제 학사, 편입생·졸업유예·초과 등록이 아닐 때만). 계산값을 실제로 쓴 공고에만 가정으로 알립니다.

**20건 실제 판정으로 확인해 보강한 것**
- 지역이 `비수도권`·`수도권`·`충청권`·`호남권`·`영남권` 같은 **권역**이거나 `중국`·`해외` 같은 **해외 지명**이면 읽습니다 (학교가 경기 시흥이면 `비수도권`·`중국`은 미달).
- 학적 상태 목록(`required_status`)은 **둘 중 하나**로 읽습니다: 재학과 휴학은 동시에 될 수 없으므로 `["재학", "휴학"]` 은 재학생도 휴학생도 가능하다는 뜻입니다 (v2 는 그대로).
- **학교 소재지**는 학생 입력이 아니라 서버 설정입니다. `.env` 에 `RECOMMEND_SCHOOL_SIDO=경기도`, `RECOMMEND_SCHOOL_SIGUNGU=시흥시`, `RECOMMEND_SCHOOL_TYPE=GENERAL` 을 설정하세요. **설정하지 않으면 학교 소재지 조건(서울 소재 대학, 비수도권 대학 등)이 모두 '확인 필요'로 남습니다.** `run_v3_match.py` 는 설정이 없으면 시작할 때 알려 줍니다.
- 학생의 `부모 주민등록`은 하나의 값입니다. 공고가 `부 or 모`를 요구하는데 부모의 거주지가 서로 다르면 맞지 않을 수 있습니다.

## 판정 엔진 v3 - 4-B1: 신분·면제·나이·계열 + 별도 표기

**판정(충족·조건부·미달)에 쓰는 것**
- **신입생 성적 면제**: 이수 0학기이고 편입이 아닌 학생은 직전학기 성적이 없으므로 **공고에 면제 문구가 없어도** 평점·직전학기 학점 조건을 면제합니다 (입학성적 기준은 입력받지 않아 확인 필요, 이수 학기 수 조건은 면제가 아님).
- **면제(waivers)**: 신입생·편입생(입학구분)·신분(장애 등)이 해당하면 면제 항목(성적·학점·소득·지역)을 충족으로 처리하고 이유를 표시합니다. 재입학·복학은 입력 항목이 없어 '면제일 수 있음'으로 보고 **미달을 탈락시키지 않고 확인 필요**로 낮춥니다. 편입 모드(성적 요건 없음 / 전적대 성적)도 같은 방식입니다.
- **필수 신분**: 나열된 신분 중 **하나만 해당하면 충족**. 모든 신분 항목에 답했는데 해당이 없으면 미달, 일부만 답했으면 확인 필요. 신분과 소득이 같은 곳에 함께 있으면 공고가 '또는'인지 '그리고'인지 불명확할 수 있어 **두 해석이 같은 결과일 때만 단정**합니다.
- 나이·성별·입학년도·편입 제외·**학과 계열**(학생 입력의 `학과 계열`과 공고의 허용 계열 비교)·**학교 종류**(서버 설정 `RECOMMEND_SCHOOL_TYPE`과 비교. 사이버·방송통신·사내대학 제외 공고는 일반대학·전문대학에는 해당 없음).
- **조건이 하나도 구조로 담기지 않은 유형**(이름·금액·마감일뿐인 유형. 공고가 '유형별 선발조건은 공고문 확인'이라고 한 경우)은 `충족`이 아니라 **`조건부`**: `이 유형의 선발 조건이 공고 본문에 없음 (공고문 확인 필요)`. 우대 신분만 있는 유형도 같습니다. (4학년 수도권 학생에게 `지역인재장학금 충족`이라고 하지 않기 위함)
- 자격을 문장으로 적은 조건(`other_conditions`)은 코드가 해석하지 않고 확인 항목으로, 학적·등록 상태 제외 문구(휴학생 제외 등)는 판정에 씁니다.
- 아직 판정하지 않는 것: 소득의 중위소득 %·재산·직업 기준·서술형(자격 조건이라 **확인 필요**로 남김).

**판정에 영향을 주지 않고 따로 표시하는 것** (결과의 `prerequisites` / `preferences` / `school_programs` / `notes`)
- **선행 조건**: 국가장학금 신청(`충족`/`신청 필요`/`확인 필요`), 학자금 지원구간 산정(입력된 구간이 있으면 충족), 학위 소지(`미충족` 포함), 입학허가·교환학생 선정(확인 필요).
- **우대 조건**: 우대 신분(`해당`/`해당 없음`/`모름`). 유형별 우대도 유형 이름과 함께 표시.
- **학교 참여 사업**: 국가장학금·지역인재·주거안정 참여대학 조건과 본교 참여 여부. 본교 참여 여부는 `.env` 의 `RECOMMEND_SCHOOL_PROGRAMS`(쉼표로 여러 개) 설정이며, 없으면 '설정 없음'으로 표시합니다.
- **확인 사항**: 중복수혜·기수혜 제한, 혜택 제한, 절차·서류, 선발 후 의무, 심사 기준, 추천 필요. 표시 순서는 항상 같습니다.
- 유형별 신청 시작·마감도 해당 가능 유형과 함께 표시합니다 (예: `대학생(충족, ~10-07)`). 기준일(`--today`, 기본은 오늘)보다 **마감이 지난 유형**은 `성취 장학(대학생)(충족, ~09-08 마감 지남)` 처럼 표시합니다 (마감 당일은 지난 것이 아님).

**학생 입력**: `학과 계열`(예: `공학`, `공학계열`)을 학교 시스템에 이미 분류된 값 그대로 받습니다. 표시 이름과 표준 코드(`HUMANITIES`, `SOCIAL`, `NATURAL`, `ENGINEERING`, `MEDICAL`, `ARTS_PE`, `EDUCATION`, `AGRICULTURE`)의 연결은 항목 사전(`config/item_registry.json`)의 `enum` / `enum_codes` 에 있어 **학교의 계열 이름으로 코드 수정 없이 바꿀 수 있습니다.** 이 항목은 공고 경로가 없는 학생 입력 전용이라 **AI 프롬프트에 들어가지 않습니다.**

**출력 모양**: `run_recommend.py` 와 `run_v3_match.py` 의 결과는 **표**가 기본입니다 (`--format table`). 충족·조건부마다 `요약` 표(글번호·장학금·마감·해당 가능 유형·확인 필요)와 `선행 조건 · 우대 조건 · 학교 사업 · 확인 사항` 표가 나오고, 끝에 **원문 링크 표**(판정·글번호·원문)가 붙습니다. 한글은 두 칸으로 계산해 정렬하며, 줄 그리기 문자 대신 `+---+`, `|` 를 써서 한국어 콘솔에서도 열이 어긋나지 않습니다. 긴 내용은 칸 안에서 줄바꿈하고, **원문 주소는 줄이거나 나누지 않습니다** (열 수 있어야 하므로). 마감·경고가 하나도 없으면 `마감` 열을, 부가 정보가 없는 공고(v2 등)는 두 번째 표를 생략합니다.
- `--format md`: 마크다운 표 (채팅·문서에 붙여넣기용, 장학금 이름이 원문 링크가 됨) / `--format list`: 예전 목록 모양 / `--width N`: 표의 최대 폭(기본: 터미널 폭, 알 수 없으면 120).
- 원문 주소는 추천 결과에서는 DB 의 원문 주소를 쓰고, `run_v3_match.py` 에서는 시험 추출 결과에 저장된 주소(`url`) 또는 글번호로 만든 드림스폰 주소(`https://www.dreamspon.com/scholarship/view.html?idx=글번호`)를 씁니다 (`EXT02_BASE_URL` 로 기본 주소 변경).
- `run_v3_match.py --detail 글번호` 는 그 공고의 모든 판정 항목(공통·유형별)과 별도 표기를 한 표로 보여 주고 원문 주소를 표 아래에 한 줄로 냅니다.

**직접 확인하기**
```
python run_v3_match.py --profile-text sample_student.txt                 # v3_trial\ 의 공고 전체를 판정 (공고별 한 줄, 크레딧 0)
python run_v3_match.py --profile-text sample_student.txt --detail 9098   # 한 공고의 모든 판정 항목과 [별도] 표기
```
`AI_SCHEMA_VERSION=3` 은 **가상 학생 시험(4-B2)이 끝나기 전에는 켜지 마세요.**

## 4-B2 일치 시험: 가상 학생 × 공고 × 학교 (크레딧 0)

판정 엔진이 실제 공고에서 틀리지 않는지 확인하는 시험이다. 가상 학생 **30명** × 시험 추출 공고 **20건** × 학교 **5개**(시흥·성북·해운대·유성·안산 전문대) = **3000쌍**을 엔진으로 판정하고, **공고 원문을 사람이 읽고 만든 정답**과 대조한다.

- 자료: `data/v3_matrix/notices/` (20건 고정, 이메일·전화번호 마스킹), `data/v3_matrix/students.txt` (학생 30명, 학생마다 시험하려는 경계·모호성을 설명에 적음)
- 정답 규칙: `scholarship/recommend/matrix_truth.py` (**엔진 코드를 쓰지 않고** 원문 조건만 독립적으로 구현). 정답은 세 가지다: `미달`(확실히 대상 아님) / `불확실`(학생 정보로 판단할 수 없는 조건이 남음) / `충족`(모든 조건 확인).
- 실행: `python run_v3_matrix.py` (`--pair s14:9217` 한 쌍의 상세, `--show all` 알려진 한계까지, `--notices v3_trial` 내가 추출한 결과로, `--strict` 심각한 불일치가 있으면 종료 코드 1)

| 분류 | 뜻 | 심각도 |
|---|---|---|
| 거짓 탈락 | 엔진 미달 / 정답은 미달 아님 | 가장 심각 (받을 수 있는 학생을 탈락시킴) |
| 거짓 통과 | 엔진 충족 / 정답은 미달 확정 | 심각 |
| 과신 | 엔진 충족 / 정답은 불확실 | 심각 (확인할 조건이 남았는데 충족이라고 함) |
| 조건부로 통과 | 엔진 조건부 / 정답은 미달 확정 | 경미 |
| 알려진 한계 | 위와 같지만 설계상 한계 (읍·면·동 이름이 다른 경우, AI 가 놓친 조건) | 정보 |
| 과소 확신 | 엔진 조건부 / 정답은 충족 | 정보 |

**결과: 3000쌍 중 2975쌍 일치**, 거짓 통과 0, 과신 0, 조건부로 통과 0, 거짓 탈락 5(9144 한 학생: 재추출 전의 `[3]`), 알려진 한계 10, 과소 확신 10.
`tests/test_v3_matrix.py` 의 `ACCEPTED` 표가 허용하는 불일치와 이유를 기록하며, 엔진·프롬프트가 바뀌어 새 불일치가 생기면 테스트가 실패한다.

**이 시험이 찾아 고친 엔진 오류**
- 누적 평점 기준(`전체 평점 백분위 85점`)을 **직전학기 백분위**로 비교하던 오류 (거짓 탈락·거짓 충족): 직전학기 기준은 `직전학기 백분위`로, 누적 기준은 `누적 백분위`로만 비교하고 입력이 없으면 확인 필요.
- `중·고교 3년 재학 후 졸업`처럼 기간이 있는 졸업 학교 요건을 학교 소재지만 맞아도 충족으로 단정하던 오류: 재학 기간은 입력 항목이 없어 확인 필요.
- 신분(공고 전체)과 소득 상한(유형 안)이 나뉘어 있으면 `그리고/또는` 모호성을 단정하던 오류(9217): 신분을 유형으로 내려 소득과 함께 판정하고 한쪽만 충족이면 확인 필요.
- 읍·면·동 이름이 **정확히 같은데도** 확인 필요로 두던 것: 정확히 같을 때만 충족으로 본다 (다르면 법정동·행정동 표기 차이가 있어 미달로 단정하지 않음).
- **AI 가 구조화한 조건을 엔진이 읽지 않던 누락 2건** (조용히 무시되어 거짓 통과가 될 수 있었다): `new_student_only`(9066 `4년제 대학 신입생`)와 `language_requirements`(9141 `HSK 5급`). 스키마의 모든 조건 필드가 엔진에서 읽히는지 검사하는 가드 테스트(`test_every_schema_condition_field_is_read_by_the_engine`)를 추가했다. 판정에 쓰지 않는 필드는 이유와 함께 `NOT_JUDGED` 에 적어야 한다.

**학생 입력 추가**: `누적 백분위`(공고의 전체 평점 기준이 100점제일 때 비교하는 누적 100점 환산 점수. `직전학기 백분위`와 다른 값이며 JSON 은 `gpa_cumulative_percent`), `어학 성적: 없음`(성적이 없다고 답한 것. 답하지 않은 것과 구분되어 어학 요건 미달 판정이 가능). 어학 요건은 나열된 시험 중 하나만 충족하면 충족이고, 등급 비교는 숫자 등급 시험(HSK·TOPIK·JLPT)에만 쓰며 OPIc 같은 문자 등급은 확인 필요다.

**프롬프트 규칙 35 (진급)**: `'N학년 진급(예정) 재학생'`은 대상 학년을 `[N-1, N]` 으로 읽는다 (9144 `3학년 진급 재학생`을 `[3]`으로 읽어 2학년 2학기 학생을 미달 처리하던 문제). 프롬프트가 바뀌었으므로 **해당 공고만 다시 추출**한다: `python run_v3_trial.py --only 9144 --force` 후 `python run_v3_matrix.py --notices v3_trial --pair s23:9144` 로 확인.

**한계**: 정답은 사람이 원문을 읽고 만든 규칙이라 틀릴 수 있다 (9237 은 정답이 과해서 고쳤다). 공고 단위로 대조하므로 **유형 내부의 오류가 다른 유형에 가려질 수 있다** (예: 9163 `재학생` 유형이 C학점 대체 기준 누락으로 미달이어도 `신입생` 유형이 조건 미상이라 공고 전체는 조건부). 유형(variants) 단위에는 `new_student_only`·어학 요건이 스키마에 없어 이름뿐인 유형(9163 `신입생`)은 조건부로 남는다. 문장 조건이 있는 공고(대부분)는 정답이 `불확실`이라 충족 판정의 검증은 9058·9096·9181·9217·9237 에 한정된다.

## 5단계 후속 질문과 결과 형식 (크레딧 0)

판정에서 `확인 필요`로 남은 항목을 **학생에게 무엇을 물으면 풀리는지**로 바꾸고, 첫 판정 뒤에 **이어서 답할 수 있게** 한다. 서버는 학생 정보를 저장하지 않는다(상태 없음).

**흐름**: 1차(학교 DB 값 + 본인 주민등록) -> 판정 + 후속 질문 -> 학생이 답 -> 2차(지금까지의 입력 + 이번 답) -> 판정 + **변화** + 남은 질문. 포털은 학생이 직접 답한 값만 임시로 보관하면 된다(학교 DB 값은 다시 가져옴).
`Recommender.recommend_step(profile, answers=..., answers_text=..., declined=[...], round_no=1)`: `answers` 는 프로필 JSON 키(질문의 `answer.keys` 가 알려 줌), `answers_text` 는 `- 라벨: 값` 줄. 틀린 값 하나가 나머지 답을 버리지 않는다(키마다 따로 검증, 사유는 `answers.warnings`).

**질문 규칙**
- 판정 항목마다 "풀어 줄 수 있는 입력 항목 후보"(`Check.needs`)를 표시하고, 이미 답한 항목은 걸러낸다 (값이 있는데도 확인 필요인 경우는 질문이 되지 않는다).
- 학생이 답할 항목만 질문하고, **학교 DB 항목이 비어 있으면** 학생에게 묻지 않고 `data_gap`(포털이 보낼 것)으로 알린다. 입력으로 풀 수 없는 조건(공고의 문장 조건 등)은 `document_only`(공고문에서 직접 확인).
- 순서: 일반 항목 먼저, **민감 항목(신분)은 마지막**. 같은 그룹에서는 더 많은 공고를 확정시키는 항목 순. 거주 기간은 본인 주민등록을 받은 뒤에 묻는다.
- 한 번에 최대 5개, 최대 3회. 건너뛴 항목(`declined`)은 다시 묻지 않는다.

**실행**: `python run_recommend.py --profile-text 1차입력.txt --follow-up` (질문 표), `--answers 답변.txt --round 2` (답을 넣고 변화 표 + 남은 질문), `--declined SPECIAL,AGE`, `--max-questions N`, `--json`.
**내 시험 추출 공고로 바로 확인**: `python run_v3_match.py --profile-text 1차입력.txt --follow-up` (같은 옵션: `--answers`, `--declined`, `--round`, `--max-questions`, `--json`). DB 없이 `v3_trial\` 의 공고를 쓰고 마감 필터는 쓰지 않으며, 지난 마감은 `(마감 지남)`으로 표시한다.

**결과 JSON 형식 v1**: `docs/result_format_v1.md`(설명), `docs/result_v1.schema.json`(JSON Schema draft-07). `result_version` 은 필드를 더하는 변경은 그대로, 필드를 없애거나 뜻을 바꾸면 올린다. 포털은 모르는 필드를 무시한다. 코드(`result_format.py`)가 원본이고, 스키마 파일·문서가 코드와 다르면 테스트가 실패한다
(스키마 파일을 고칠 때: `python -m scholarship.recommend.result_format --write`).

**시뮬레이션**(학생 30 × 학교 3 = 90번의 대화, `tests/test_result_format.py`): 대화가 끝난 뒤의 판정이 **처음부터 모든 정보를 줬을 때와 90건 모두 같다.** 질문은 학생당 평균 4.1개(최대 5개), 87건이 2회, 3건이 1회로 끝난다.
공고 1800쌍에서 `조건부` 1015 -> 552(46% 감소), `미달` 752 -> 1211. 정보를 더 줘도 `미달`이 되살아나는 경우는 없다. 남은 `조건부`는 대부분 공고의 문장 조건이라 질문으로는 풀리지 않는다.

**계약상 주의**: 성적 값(`gpa_last`, `gpa_cumulative`)을 보낼 때는 **만점 `gpa_scale` 을 함께** 보낸다. 항목 사전의 어떤 `profile_field` 에도 없는 동반 키라서 놓치기 쉽다. 보내지 않으면 4.5로 가정하고 `profile_notes.assumptions` 에 알린다(4.3점 만점 학교 학생이 잘못 판정될 수 있다).
사전에 없는 동반 키(`gpa_scale` 등)는 `tests/test_result_format.py` 의 `COMPANION_KEYS` 에 이유와 함께 등록해야 하며, 새 키가 생기면 테스트가 실패한다(6단계 계약서에 적을 목록).

**함께 고친 것**: 개발용 결과 폴더(`FileSource`)가 v3 공고를 v2 규칙으로 정리해 확장 조건을 조용히 버리던 문제(운영 DB 경로는 영향 없음).

## 6-A API 계약 (포털 연동)

포털(교내 통합정보시스템)이 228번 서버의 추천 API를 JSON으로 호출한다. 이 단계는 **계약과 입력 검증**까지이고 HTTP 서버는 6-B 에서 만든다. 학교 DB(학적·성적·소득구간)는 포털만 읽고, 추천 API는 포털이 보낸 JSON과 공고 DB만 본다.

| 산출물 | 위치 |
|---|---|
| 계약서 (역할, 호출 흐름, 인증·개인정보 규칙, 요청 필드, **프로필 필드 표**, 입력 검증, 오류 코드, 연동 시험) | `docs/api_contract_v1.md` |
| OpenAPI 3.1 명세 (포털 개발팀이 클라이언트 코드를 만들 수 있다) | `docs/openapi_v1.json` |
| 응답 형식 | `docs/result_format_v1.md`, `docs/result_v1.schema.json` |
| **연동 시험용 샘플**: 학생 30명의 첫 호출 요청과 기대 결과 | `docs/samples/api_samples.json` |

**코드가 원본**이고 문서·명세·샘플이 코드와 다르면 테스트가 실패한다. 다시 쓰기(PowerShell 의 `>` 는 UTF-16 으로 저장하므로 `--write` 를 쓴다):
`python -m scholarship.recommend.profile_contract --write-docs` (계약서의 필드 표), `python -m scholarship.recommend.api_spec --write`, `python -m scholarship.recommend.samples --write`, `python -m scholarship.recommend.result_format --write`.

**입력 검증** (`scholarship/recommend/request.py`, HTTP 와 무관한 순수 함수 `handle_recommend(recommender, body) -> (상태, 본문)`)
- 요청 구조가 틀리면(`profile` 이 객체가 아님, `round` 범위 밖 등) 판정하지 않고 `400 INVALID_REQUEST` 와 **필드별 사유**. 틀린 항목을 한꺼번에 알린다.
- **프로필의 값 하나가 틀려도 거절하지 않는다.** 그 키만 빼고 나머지로 판정하고 `profile_warnings` 에 알린다. 각 값은 맞는데 서로 모순이면(`gpa_last 4.4` 와 `gpa_scale 4.0`) `400 INVALID_PROFILE`.
- 이름·학번 같은 개인정보 키는 받지 않고(`profile_notes.dropped_sensitive_keys`) **응답에 값을 되돌려 주지 않는다.** 서버 설정 오류(`SERVER_CONFIG`)는 환경설정 내용을 노출하지 않는다.
- 응답에 `request_id`(요청 번호 그대로)와 `profile_warnings` 가 붙는다 (결과 형식 v1 에 선택 필드로 추가).

**필드 계약** (`profile_contract.py`): 키·출처(학교 DB / 학생)·등급·민감 여부는 항목 사전에서, 형식·허용 값·예시는 코드에서 정한다. **모든 예시와 허용 값이 실제 프로필 검증을 통과하는지** 시험한다. 사전에 없는 동반 키(`gpa_scale` 등)도 표에 들어 있다.

## 입력 보강 P1~P6 (포털이 보내는 값의 정확도)

원칙: **맞으면 맞다, 모르면 모른다(`확인 필요`), 틀린 것을 맞다고 하지 않는다.** 조용히 거짓 탈락으로 이어지던 입력을 찾아 막았다. 허용 범위는 `docs/api_contract_v1.md` 의 필드 표(`허용 범위·값` 열)가 정하며, 표의 숫자 범위는 **코드가 받아들이는 경계와 정확히 같은지 시험**한다.

| | 내용 |
|---|---|
| **P1** | 시·도는 **17개 공식 이름**만 받는다 (`vocab.canon_sido`). 약칭·옛 이름(`경기`, `대구시`, `강원도`)은 공식 이름으로 바꿔 저장, **오타(`서울틐별시`)는 거절하고 알림**. 지명 파서가 `대구광역시`를 `대구`+`광역시`로 쪼개 대구 학생이 탈락하던 결함 수정 |
| **P2** | 국적을 `KR` / `FOREIGN` / `OVERSEAS_KR` 로 정리(`Korean`, `한국인`, `내국인`, `재외동포` …). 알 수 없는 값은 거절 (조용히 내국인 대상 공고에서 탈락시키지 않는다) |
| **P3** | JSON 키의 공백·대소문자·하이픈 차이는 계약의 키로 읽는다. 알 수 없는 키는 무시하고 **`profile_warnings` 로 알린다** |
| **P4** | 텍스트 라벨 동의어 추가 (`현재 학년`, `몇 학년`, `지난 학기 평점`, `연령`, `소속 학과`, `등록 학기 수`, `부모님 주소`, `부모 거주지`). **뜻이 갈리는 `학점`(평점/취득학점), `거주지`(본인/부모)는 일부러 넣지 않고 경고로 되묻는다.** `주소`는 개인정보로 걸러낸다 |
| **P5** | **엄격 모드** `"strict": true`: 판정은 그대로 하고 응답에 `contract_violations`(계약과 한 글자라도 다른 입력)를 더한다. 포털 변환 코드 시험용. 운영은 관대하게 받는다 |
| **P6** | 범위 강화: 문자열 길이(학과 100자, 시·군·구 40자), `term_history` 최대 20개, 거주 기간 0~100, 어학 점수 0~1000, 불리언·배열은 JSON 형식만(`"true"`, `1`, 단일 문자열 신분, `"780"` 은 받지 않고 알림), `gpa_last` 가 `term_history` 해당 학기 평점과 다르면 경고 |

**측정(같은 실험의 보강 전 -> 후)**: 값 표기 변형 조용한 오류 1 -> 0, 시·도 표기 45건 정확 43 -> 45(대구 2건 해소), 동명 지역(시·도 없이 시군구만) 17개 요건 `미달` 3 -> 0(모두 `확인 필요`), 텍스트 자연어 라벨 39개 중 인식 17 -> 26(잘못 인식 0).
순서는 이미 안전했다: JSON 키 순서·텍스트 줄 순서·`term_history` 순서를 섞어도 결과가 같다(300회).

**알아둘 점**
- 시·도 칸에 `경기도 수원시` 한 줄을 넣거나(예전에는 우연히 맞았다) 시·도와 시군구를 바꿔 넣으면 이제 **거절하고 알린다.** 포털이 `residence_sido` / `residence_sigungu` 를 나눠서 보내야 한다.
- 코드로 못 푸는 것: 한글 숫자(`스물넷`)·영문 지명·자연어 문장(거절하고 알림, 필요하면 8단계의 AI), 같은 이름의 다른 지역(되묻기가 정답), **의미 오류**(부모 주소를 본인 칸에 넣음, 만점을 잘못 보냄)는 엄격 모드와 연동 시험 샘플로 막는다.
- `entry_year` 의 상한(올해+1)은 엄격 모드에서만 검사한다 (운영은 2100까지).

## 추천 단계 (RECOMMEND) - 학생 프로필과 공고 비교

저장된 공고(`SCHOLARSHIP_NOTICE.ELIG_JSON`)와 학생 프로필(개인정보 제외)을 **코드로 비교**합니다 (AI 호출 없음).

```
python run_recommend.py --profile student.json --results-dir out     # DB 없이 --dump-dir 의 결과 파일로 시험
python run_recommend.py --profile student.json                       # 저장 DB 의 공고로 (config/recommend_query.txt)
python run_recommend.py --profile student.json --json               # 서비스 연동용 JSON
옵션: --today 2026-10-06 (기준일), --show-excluded (미달 목록과 사유)
```

- **판정**: 조건마다 충족/미달/알 수 없음. 학생 정보가 없으면 탈락시키지 않고 `조건부(확인 필요)`. 결과는 **충족**(확인 항목 없음) / **조건부** / **미달**(사유 포함).
- **variants**: 공통 조건(최상위)을 만족하고, 유형이 없거나 **어느 한 유형이라도** 만족하면 후보. 결과에 해당 가능 유형과 미달 유형이 함께 나옵니다.
- **코드가 판정하지 않는 것**: 문장으로만 적힌 조건(`other_conditions`, `special_status` 일부, 제외 조건 일부)은 **확인 항목**으로만 돌려줍니다. 그래서 이런 조건이 있는 공고는 `충족`이 아니라 `조건부`가 됩니다.
- **성적**: 만점 단위가 같으면 직접 비교, 4.5/4.3/4.0/5.0 끼리는 비율 환산(경계 ±2%는 판정 안 함), 100점제와 4.x 는 학생이 `gpa_percent` 를 줄 때만 비교.
- **구형식**(`schema_version` 없음, variants 없음) 결과: 유형별 조건이 합쳐져 있을 수 있어 성적/학점/소득의 미달을 `확인 필요`로 낮추고 경고를 붙입니다 (거주지·학적 같은 공통 조건은 그대로 판정).
- **중복 공고**: 재단+장학명이 같은 공고(원 공고/연장 공고)는 최신 공고로 묶고 `merged_from`/경고로 알립니다 (`RECOMMEND_DEDUPE=false` 로 끔).
- **경고**: 마감 임박/오늘 마감, 신청 시작 전, 추천서 필요, 재단 마감일 상이, 검수 대기(`NEED_REVIEW`), 검수 사유(`verify`), 구형식, 공고 묶음.
- **개인정보**: 이름·학번·주민번호·연락처·이메일·상세 주소 등(`home_address`, `E-mail` 같은 변형 포함)은 받지 않고 버립니다 (버린 항목 이름만 알림). 결과 사유 문구에는 학생의 평점·학점 같은 속성 값이 들어갈 수 있으므로 **그 학생에게만** 전달하세요.
- **거주 조건의 대체 요건**: 공고 안내문(`region.notes`)에 `자녀·부모·가족·출신·졸업·고등학교` 같은 표현이 있으면(예: "시민 또는 그 자녀") 본인 주민등록이 달라도 **탈락시키지 않고** `확인 필요`로 둡니다.
- **코드 탈락 보류 (`RECOMMEND_DEFER_KEYS`)**: 지정한 조건 종류(`region`, `gpa` 등)는 미달이어도 탈락시키지 않고 `확인 필요 [AI 판단 예정]`으로 남깁니다. 거주·주민등록 기준지를 나중에 AI 프롬프트로 판단하려는 경우 `region` 을 지정하세요 (기본은 비어 있어 코드가 판정).
- **마감일이 없는 공고**는 후보에서 빠집니다 (`config/recommend_query.txt` 의 `APPLY_END >= :today`).

### 알려진 한계

- 추출 결과가 틀리면 판정도 틀립니다. `NEED_REVIEW`/구형식 공고는 경고를 붙여 원문 확인을 안내합니다.

- `성적향상` 같이 학교급이 다른 유형은 **새 형식(variants[].target_levels)으로 다시 추출한 공고**에서만 코드로 걸러집니다. 이전에 저장된 결과는 확인 항목으로 남습니다.
- 같은 장학의 공고 이름이 서로 많이 다르면 묶이지 않을 수 있고, 이름이 같은 다른 공고가 묶일 수 있습니다 (묶임은 결과에 표시).

## 이미 저장된 글 처리 (건너뛰기 규칙)

| 상황 | 동작 |
|---|---|
| 글번호가 있고 **완료**(EXTRACTED / NEED_REVIEW) + 내용 같음 | 건너뜀 (`변경없음`) |
| 글번호가 있고 완료 + **내용이 바뀜** | **건너뜀** (`건너뜀(내용변경)`, 로그에 표시). 재처리: `--update-changed` 또는 `--force` |
| 글번호가 있고 **미완료**(COLLECTED / FAILED) | 이어서 처리 / 재시도 (건너뛰지 않음) |
| 글번호는 새 글인데 **제목이 같은 활성(USE_YN=Y) 글**이 있음 (공백·HTML 엔티티 정리 후 비교) | 건너뜀 (`건너뜀(제목중복)`, AI 호출 없음). 끄기: `--no-skip-title` |
| 원본에서 삭제되어 `USE_YN=N` 인 글과 제목이 같음 | 건너뛰지 않음 (재게시로 봄) |
| `--force` | 위 규칙을 모두 무시하고 다시 처리 |

- 주의: 공고가 **수정되어 마감일이 연장**돼도 기본 설정에서는 반영되지 않습니다. 실행 요약의 `건너뜀(내용변경)` 건수를 확인하세요.
- `.env`: `SKIP_SAME_TITLE=false`, `UPDATE_CHANGED=true` 로도 바꿀 수 있습니다.

## AI 응답이 "JSON 이 아님"으로 실패할 때

- 가장 흔한 원인은 **응답이 출력 한도(max_tokens)에서 잘림**입니다 (긴 공고, 항목이 많은 표). 기본 한도는 16000 토큰(`AI_MAX_TOKENS`, 쓴 만큼만 과금)이고, 잘리면 자동으로 2배(최대 `AI_MAX_TOKENS_LIMIT`=24000)로 올려 다시 호출합니다. 긴 응답은 생성에 1~2분이 걸리므로 `AI_TIMEOUT` 은 300초 이상을 권장합니다.
- 파서는 앞뒤 설명문, 코드블록, 객체 뒤 잔여 텍스트, 문자열 안 줄바꿈, 끝의 쉼표를 허용합니다. 잘려서 닫히지 않은 JSON 은 일부 값만 있는 결과를 만들지 않기 위해 복구하지 않습니다.
- 실패하면 `UNCERTAIN_JSON` 에 오류 사유, **중단 사유(stop_reason)**, 시도 횟수, 출력 토큰, 응답 원문의 앞/뒤 일부가 저장되고, `--dump-dir` 를 쓰면 `ext01_글번호_ai_raw.txt` 에 원문 전체가 저장됩니다.
  - 중단 사유 `max_tokens` -> 한도 문제 (`AI_MAX_TOKENS` 상향)
  - 중단 사유 `end_turn` 인데 JSON 이 아님 -> 모델이 설명문/거절로 답한 경우. 원문 앞부분 확인

## AI 추출 결과(ELIG_JSON) 읽는 법

- **모델**: `AI_MODEL=claude-sonnet-5-5` (Claude Sonnet 5.5, 게이트웨이 모델 id). 코드 기본값도 같습니다. `python set_secret.py --models` 로 확인.
- **스키마 버전**: 저장되는 `ELIG_JSON` 의 `schema_version`. 없으면 v1(구형식), 2 이면 `variants`/`apply_how` 가 있는 형식. 구형식 결과만 골라 재처리할 때는 `check_ext01.sql` 8번을 쓰고 `--force --only 글번호...` 로 다시 처리합니다.
- **`variants` (유형별 조건)**: 장학금 안에 자격이 다른 유형이 둘 이상일 때 유형별로 담습니다.
  - 최상위 값 = **모든 유형에 공통**인 조건, `variants[].…` = 공통에 **추가로** 요구되는 조건 (null/빈 값 = 그 유형에 추가 조건 없음).
  - 유형마다 다른 항목(예: 성적 기준)은 최상위에서 null 로 두고 유형별 값을 씁니다.
  - 유형이 특정 학교급만 대상이면 `variants[].target_levels` 에 적습니다 (비우면 최상위와 같음). 최상위 `target_levels` 는 모든 유형의 합입니다. 특정 학교·학교 종류(원격대학, 특정 대학) 조건은 `other_conditions` 텍스트에 있으므로, 코드가 판정할 수 없는 유형은 "AI 확인 필요"로 다룹니다.
  - AI 는 값이 있는 키만 적고(null/빈 값 생략), 코드가 빈 항목을 기본값으로 채워 저장합니다. `--dump-dir` 의 `ext01_글번호_ai_raw.txt` 가 AI 가 실제로 쓴 원문입니다.
  - 등급(장려/우수/최우수)처럼 금액·점수만 다른 경우는 `variants` 로 나누지 않고 `amount`/`other_conditions` 에 요약합니다. `variants` 가 비어 있으면 유형 구분이 없는 공고입니다.
  - **추천 판정 규칙(안)**: 학생이 `공통 조건`을 모두 만족하고, (`variants` 가 비어 있거나 **어느 한 유형이라도** 그 유형의 조건을 만족)하면 후보. (이 규칙은 추천 단계에서 구현 필요)
- **`apply_how`**: 신청 방법·접수처 한 줄 (구글폼/우편/추천서 필요 등). 자격 조건(`other_conditions`)과 분리되어 있습니다.
- **`target_levels`**: 공고가 대상으로 하는 학교급 **전체** (대학생이 아니어도 빼지 않음). 학생에게 맞는지는 추천 단계에서 거릅니다.
- 출력 간결 규칙(문장 60자, 서류 12개 등)이 적용되어 있어 `documents` 는 서류 이름만, `evidence` 는 위치만 담습니다.

- `income.eligible_types` 는 서로 **"또는"** 관계의 선택지이고, `income.max_bracket` 은 그 중 **학자금지원구간(소득분위)** 선택지에만 적용됩니다. 추천 단계에서 `max_bracket` 하나만 보고 거르면 수급자/차상위 학생이 탈락하므로 `eligible_types` 와 함께 해석하세요.
- `other_conditions` : 어학 성적, 자격증, 수상, 가족돌봄 같은 **구조화되지 않는 조건**(한 줄씩). 학생 프로필에 해당 값이 없으면 "확인 필요"로 안내합니다.
- `UNCERTAIN_JSON` 의 `uncertain[].level` : `verify` = 값이 틀렸거나 빠졌을 수 있어 사람이 원문 확인(이것이 있으면 `NEED_REVIEW`), `note` = 단순 참고(상태에 영향 없음). `field` 는 어느 값인지.
- 첨부 텍스트가 깨진 표 등은 AI 가 `verify` 로 표시합니다. 이런 공고는 사람이 원문을 확인하세요.

  - **`anthropic` + `AI_BASE_URL=https://factchat-cloud.mindlogic.ai/v1/gateway/claude` (권장)** : Anthropic 네이티브 Messages API. 요청이 변환 없이 전달되어 이미지/PDF/프롬프트 캐싱을 그대로 쓴다. `POST {AI_BASE_URL}/v1/messages`, 헤더 `x-api-key`. **주소는 반드시 `/claude` 로 끝나야 함**
  - `gateway` + `AI_BASE_URL=https://factchat-cloud.mindlogic.ai/v1/gateway` : OpenAI 호환 Chat Completions. `POST {AI_BASE_URL}/chat/completions`, 헤더 `Authorization: Bearer`
  - `anthropic` (AI_BASE_URL 비움) : Anthropic 직접 호출 / `openai` : OpenAI 직접 호출
  - 키는 `python set_secret.py AI_API_KEY` (게이트웨이는 TU AI Agent 에서 발급한 키, 크레딧은 **키를 만든 계정**에서 차감)
  - `AI_MODEL` 은 게이트웨이가 제공하는 모델 id (예: `claude-sonnet-5`, `claude-haiku-4-5-20251001`). 내 계정에서 쓸 수 있는 목록: `python set_secret.py --models`
  - 크레딧 잔액: `python set_secret.py --credits` (`--test-ai` 에도 함께 표시)
  - 게이트웨이 제한: 회원당 60초에 120건(429, `Retry-After` 존중), 요청 본문 25MB(413 - 이미지 원본 합계를 15MB 로 제한), 크레딧 소진은 402(재시도 안 함), `User-Agent` 가 비면 Cloudflare 403(1010) -> 항상 전송
  - 이미지를 보내지 않으려면 `AI_VISION=false` (해당 공고는 `NEED_REVIEW`)
  - 첫 확인: `python set_secret.py --test-ai` (호출 주소/모델/키 + 크레딧), 이미지 공고 1건으로 이미지 입력도 따로 확인

## 검증된 것 / 아직 검증 못 한 것

검증됨 (테스트 통과): 본문 정리(실샘플 2종), 파일명 분류, HWP 4건 추출(표·글상자), DOCX/XLSX/PDF(텍스트·스캔)/이미지(분할)/ZIP,
AI 응답 파싱·스키마 검증·요일 오기 탐지, 증분/변경 감지, 삭제 글 비활성화, 실패 격리, 저장 SQL 형태(UPDATE -> INSERT, 중복 바인드 없음).

**실제 환경에서 처음 확인해야 하는 것**
- 저장 SQL 의 실제 실행: 첫 실행에서 MERGE 가 ORA-22284(긴 값 중복 바인드)로 실패해 UPDATE -> INSERT 로 변경함. 변경 후 실제 Oracle 11g 실행 결과 확인 필요
- 실제 AI API 호출 (키·모델명·응답 형식) — 가짜 AI 로만 검증. 이미지 포함 호출 포함
- 첨부 다운로드 URL(`.../download.do`)과 본문 이미지 URL 을 228번 서버에서 호출 (curl -I)
- HWPX: 합성 샘플로만 확인 (실제 파일 필요), 구형 .doc/.xls/.ppt 는 미지원(SKIPPED)
- HWP 변환이 실패하면 (배포용·암호·DRM·구버전·손상 등) 로그에 **원인(문서 버전/플래그, pyhwp 오류)** 을 표시하고, 파일 안의 **미리보기 텍스트(앞부분 약 1,000자)** 만이라도 추출해 `일부만 추출됨` 으로 AI 에 알리고 공고를 `NEED_REVIEW` 로 표시합니다. 미리보기도 없으면 첨부 `FAILED` (요강이 이 파일에만 있으면 사람이 원본을 확인해야 함)
- HWP 의 병합 셀 값은 첫 행에만 나옴 / 하이퍼링크 텍스트 소실 → AI 단계에서 보정하고 불확실이면 `NEED_REVIEW`
- 초기 1~2개월은 `NEED_REVIEW`/`FAILED` 건과 첨부 `FAILED` 사유를 확인해서 키워드·규칙을 보정할 것
